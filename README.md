# ЕДИН — Единый сервис идентификации физических лиц

ЕДИН — Master Person Index (MPI), обеспечивающий определение единого физического лица по данным из различных информационных систем и выдачу стабильного ИД.

Внутреннее имя сервиса: **Mnemonios** (Мнемоний).

---

## Назначение

**ЕДИН — единый сервис идентификации физических лиц для корпоративных информационных систем.**

Сервис обеспечивает однообразное определение физического лица по данным из различных корпоративных систем (CRM, ERP, HR, бухгалтерия и др.) и выдачу стабильного идентификатора (`PersonID`), действующего на протяжении всего жизненного цикла записи.

### Границы использования

**Сервис предназначен для:**
- Единой идентификации физических лиц внутри корпоративного контура
- Сопоставления записей из разных информационных систем
- Предоставления стабильного внутреннего ИД для кросс-системной интеграции
- Контроля качества входных данных (валидация ИНН, СНИЛС, ДУЛ)
- Автоматического обнаружения и разрешения конфликтов между системами

**Сервис НЕ предназначен для:**
- Хранения полного комплекта персональных данных (ФИО, ИНН, СНИЛС хранятся в усечённом виде для идентификации)
- Аутентификации или авторизации пользователей
- Управления доступом к ресурсам
- Передачи персональных данных третьим лицам
- Замены карточек учёта в учётных системах-источниках

> **Важно.** Хранение согласия на обработку ПДн и отзыв согласия на обработку ПДн **не являются** функциональными особенностями проекта ЕДИН. Эти функции возлагаются на одну или несколько вызывающих корпоративных информационных систем. ЕДИН предоставляет технический механизм удаления данных (`POST /persons/cessation`, `POST /persons/cessation/deferred`), но решение о необходимости отзыва принимает внешняя система-источник.

> **Ограничение передачи данных.** Вычисленные HMAC-хеши **не передаются** через API ни в ту, ни в другую сторону. Персональные данные (ФИО, ИНН, СНИЛС, ДУЛ) **не передаются** вызывающим системам через API — они хранятся в нормализованном виде исключительно для целей внутренней идентификации.

### Зачем это нужно

Одна и та же персональная информация поступает из разных систем в различных форматах, с ошибками и дублями. ЕДИН решает проблему дублирования и рассинхронизации данных о физических лицах.

**Без ЕДИН:**
- Система A знает «Иванов Иван Иванович, ИНН 7707083893»
- Система B знает «Иванов И.И., СНИЛС 12345678964»
- Система C знает «Иванов Иван, паспорт 4510 123456»
- Непонятно, одно это лицо или три разных

**С ЕДИН:**
```
Запись A ─┐
Запись B ─┼──► ИД ──► единое физическое лицо
Запись C ─┘
```

## Ключевые возможности

### Идентификация по любым доступным данным

Сервис определяет лицо по любому набору доступных данных — не обязательно полному:

| Источник данных | Типичный сценарий |
|-----------------|-------------------|
| Фамилия + Имя | Базовая идентификация |
| ИНН | Налоговый учёт, кадры |
| СНИЛС | Пенсионный фонд, медицина |
| Паспорт | Государственные услуги |
| Комбинация | Снижение ложных срабатываний |

Отсутствие какого-либо поля не препятствует сопоставлению — используются только доступные ключи.

### Устойчивость к различиям данных

Сервис автоматически устраняет расхождения:
- Разный регистр: «иванов» = «ИВАНОВ»
- Лишние пробелы: «Иванов  Иван» = «Иванов Иван»
- Различия в написании отчества: ищет и по полному ФИО, и без отчества

### Толерантная обработка ошибок

Сервис **не отказывается** от добавления сведений о лице при наличии ошибок в данных:

| Ситуация | Поведение |
|----------|-----------|
| ИНН с ошибкой контрольной суммы | Ключ вычисляется, дефект логируется |
| СНИЛС с ошибкой контрольной суммы | Ключ вычисляется, дефект логируется |
| ДУЛ с одной частью (серия без номера или наоборот) | Документ сохраняется, дефект логируется |
| Невалидный тип ДУЛ | Запрос отклоняется |

### Автоматическое разрешение конфликтов

Когда две системы присылают разные данные об одном лице → статус «Конфликт». Если одна из систем **исправляет данные** → конфликт **автоматически закрывается** без участия стюарда. История разрешения сохраняется.

### Аудит IP-адреса

Каждый запрос от внешней системы фиксируется с IP-адресом источника в staging-таблицах. Это позволяет:
- Отслеживать, какая система прислала данные
- Анализировать паттерны обращений
- Расследовать инциденты

### Централизованное логирование ошибок

Все необработанные исключения логируются через `ExceptionLoggingMiddleware` с полной цепочкой InnerException. Ошибки не «теряются» — каждая фиксируется с контекстом.

## АРМ Стюарда данных

Веб-интерфейс для мониторинга и анализа данных MPI:

| Раздел | Назначение |
|--------|------------|
| **Очередь** | Конфликты, требующие внимания стюарда |

## Как это работает

```
┌────────────────────────────────────────────┐
│           Внешняя информационная система   │
│           (CRM, ERP, HR и т.д.)           │
└──────────────────┬─────────────────────────┘
                   │ запрос + IP
┌──────────────────▼─────────────────────────┐
│                ЕДИН MPI                    │
│                                            │
│  1. Нормализация данных                    │
│  2. Валидация (ИНН, СНИЛС, тип ДУЛ)       │
│  3. Вычисление идентификационных ключей    │
│  4. Поиск совпадений                       │
│  5. Решение:                               │
│     • Matched — найдено существующее лицо  │
│     • Unmatched — создано новое лицо       │
│     • Ambiguous — конфликт (авто-закрытие) │
│  6. Фиксация IP и дефектов                 │
└──────────────────┬─────────────────────────┘
                   │ ИД
┌──────────────────▼─────────────────────────┐
│        Единая база физических лиц          │
│        (PostgreSQL 16)                     │
└────────────────────────────────────────────┘
```

## Терминология

| Термин | Определение |
|--------|-------------|
| **Master Identifier** | Мастер-идентификатор человека. Уникальный GUID, присваиваемый при создании записи. Не изменяется в течение жизненного цикла. |
| **Evidence** | Доказательства идентичности. Атрибуты, используемые для подтверждения того, что два набора данных относятся к одному лицу: ФИО, ДУЛ (тип, серия, номер), СНИЛС, ИНН. **ФИО не являются доказательствами идентичности** — они передаются как есть, без хеширования. |
| **Record References** | Ссылки на записи этого человека в других информационных системах. Передаются в поле `identifiers` запроса. Каждая ссылка состоит из: `sourceSystemId` (идентификатор системы-источника), `externalPersonId` (внешний идентификатор в этой системе), `externalPersonType` (тип записи — employee, client и т.д.) |
| **Source IP** | IP-адрес внешней системы, отправившей запрос. Фиксируется в staging-таблицах для аудита. |

## Результат

- **Один человек — один ИД** независимо от источника данных
- **Устойчивость** к ошибкам ввода и различиям форматов
- **Толерантность** — сервис принимает неполные и ошибочные данные, фиксируя дефекты
- **Безопасность** — данные хранятся в нормализованном виде, идентификационные ключи защищены HMAC
- **Аудит** — IP-адреса источников, дефекты, история конфликтов
- **Автоматизм** — конфликты закрываются при исправлении данных внешней ИС
- **Масштабируемость** — подключение новых информационных систем через добавление связи
- **Производительность** — p95 < 200ms, p99 < 500ms, до 1000 одновременных пользователей

## Быстрый старт

```bash
# 1. Поднять PostgreSQL
docker-compose up -d

# 2. Применить схему БД
docker exec -i mnemonios-postgres psql -U mnemonios -d mnemonios < tools/db/01_schema.sql

# 3. Запустить приложение
dotnet run --project src/Applications/Api
```

Swagger UI: `http://localhost:5000/swagger`
АРМ Стюарда: `http://localhost:5003`
