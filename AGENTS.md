# AGENTS.md

Руководство для AI-ассистентов, работающих с репозиторием SamorodinkaTech.Mnemonios.

---

## Правило: язык проекта — только русский и английский

- Во всех артефактах проекта (код, документация, коммиты, UI) разрешены **только русский и английский**.
- Использование других языков (китайский, немецкий, французский и т.п.) — **запрещено** без явного согласования с пользователем.
- При обнаружении текста на другом языке — **немедленно заменять** на русский или английский.

## Правило: комментарии в коде — только на русском (КРИТИЧНО)

- **Все** комментарии в коде (XML-документация, inline-комментарии, TODO, FIXME) — **только на русском языке**.
- Исключение: идентификаторы, ключевые слова языка, названия паттернов (SOLID, DRY, CQRS).
- При обнаружении комментария на английском — **немедленно заменять** на русский.

## Правило: хранение ПДн — только хеши (КРИТИЧНО)

- Проект **не хранит** в БД персональные данные (ФИО, ИНН, СНИЛС, ДУЛ) и их нормализованные копии.

## Правило: FK-связи staging-таблиц (КРИТИЧНО)

- Дочерние staging-таблицы (`ext_person_cessations`, `ext_person_deferred_cessations`) **ссылаются на `ext_persons`**, а **не** на мастер-таблицу `persons`.

## Правило: двухфазное прекращение обработки ПДн (КРИТИЧНО)

- Фаза 1 (`CeaseProcessingAsync`): пометить внешние ключи в `ext_person_cessations` (`processing_status = 'cessation'`). Золотые записи **НЕ** удаляются.
- Фаза 2 (`ReconcileAsync`): удалить помеченные staging-записи, затем если у лица нет оставшихся внешних ссылок — удалить золотые записи.
- Порядок удаления в фазе 2: staging → external_ids → keys/defects/deferred_cessations → persons.

## Правило: канарейка — обращение «Успешнейший»

- **Каждое** ответное сообщение пользователю начинается с **«Успешнейший!»** (или «Дважды Успешнейший!» для чатов агентов).
- Без исключений. Без «иногда». Без «когда уместно».
- Сообщения в чатах агентов начинать с **«Дважды Успешнейший!»**.

## Правило: приоритет основной задачи

- Основной запрос пользователя выполняется первым и до конца.
- Сопутствующие мета-правки — только после завершения основной задачи.
- Молча переходить к правкам, игнорируя заданный вопрос, запрещено.

## Правило: изменение только затронутых файлов сессии

- При обнаружении проблемы разрешается изменять **только файлы, затронутые в рамках текущей сессии**.
- Для сканирования или изменения других файлов — **спросить пользователя**.
- Исключение: автоматические кросс-ссылки от изменённых файлов.

## Правило: диагностика сложной логики перед модификацией

- Перед модификацией метода со сложной логикой (3+ уровня вложенности) прочитать **все** связанные методы и построить граф зависимостей.
- Запрещено переписывать метод «с нуля», если достаточно минимальной правки.

## Правило: все правила проекта — в AGENTS.md (КРИТИЧНО)

- Все правила кодирования, архитектурные ограничения, дисциплина вызова инструментов
  находятся **исключительно в этом файле** (`AGENTS.md`).
- `MEMORY.md` содержит кросс-сессионные знания (контекст проекта, обнаруженные факты),
  но **не** операциональные правила и **не** архитектурные решения.
- При обнаружении нового правила или паттерна — добавлять его в `AGENTS.md`,
  а не в `MEMORY.md`.
- При противоречии — `AGENTS.md` имеет приоритет.

## Правило: правила проекта — краткие, без глубокого контекста (КРИТИЧНО)

- Правила в `AGENTS.md` формулируются **кратко и конкретно** — суть запрета/требования
  в 1–3 предложениях.
- Архитектурные правила (`docs/decision_records/dr_*.md`) — аналогично:
  суть решения и следствия, без перечисления констант, методов, файлов и строк кода.
- Запрещено включать в правила подробные описания инцидентов, примеры кода на 20+ строк,
  каскадные объяснения «почему так», предыстория вопроса. Это контекст, а не правило.
- При обнаружении правила с избыточным контекстом — **сокращать** до минимума.

### Как формулировать правила

**Структура правила:**
```
### Правило: <суть запрета/требования> (КРИТИЧНО)
- Что делать / чего не делать — 1–3 предложения.
- При необходимости — код ≤10 строк.
```

**Запрещено:**
- Начинать с «Зафиксирован инцидент:» — это контекст, не правило.
- Писать «Правило:» повторно в теле — уже есть в заголовке.
- Длинные примеры кода (>10 строк) — выносить в отдельные файлы.
- Ссылки на `MEMORY.md` — если правило написано, оно самодостаточно.
- Повторять одно и то же правило в разных местах.

**Разрешено:**
- Повелительный тон: «Проверять», «Запрещено», «Использовать».
- Краткий пример кода (≤10 строк) для иллюстрации паттерна.
- Маркировка `(КРИТИЧНО)` для правил, нарушение которых критично.

## Правило: DRY — не дублировать существующий код (КРИТИЧНО)

Перед копированием кода проверять, есть ли уже существующий сервис/хелпер
для этой задачи. Дублирование — ошибка, которую нужно исправлять немедленно.

## Дисциплина работы ассистента (КРИТИЧНО)

### Причины сбоев

- Результат инструмента принимается на веру без повторного чтения файла.
- Основная задача подменяется мета-правками (документация, правила).
- Инструменты вызываются с плейсхолдерами вместо реальных данных.
- Исполнение останавливается без реального вопроса пользователю.

### Правило: последовательное исполнение (КРИТИЧНО)

- Задачи выполняются **строго последовательно**: шаг за шагом, без пропусков
  и без параллельного выполнения нескольких шагов.
- Каждый шаг проверяется перед переходом к следующему (сборка, тест, валидация).
- **Запрещено**: читать файлы по кругу без внесения изменений; дублировать
  одно и то же чтение N раз; выполнять неподтверждённые изменения.
- Перед началом — прочитать план; по выполнении каждого шага — проверить
  результат (сборка, grep, diff); при ошибке — **немедленно исправить**
  и перепроверить, а не продолжать к следующему шагу.

### Правило: сначала ответ на вопрос, потом действие

Если пользователь задал явный вопрос — сначала даётся содержательный ответ на этот
вопрос в тексте, и только после этого (или вместе с этим) выполняются
правки файлов. Молча переходить к правкам файлов, игнорируя заданный
вопрос, запрещено.

### Правило: уточнение затрагиваемых модулей перед реализацией (scope creep)

Перед реализацией задачи, затрагивающей более одного модуля, явно уточнить
полный список затрагиваемых модулей. Реализация ограничивается ровно тем
скоупом, который запросил пользователь. Дополнительные изменения — только
по явному запросу.

### Правило: дисциплина вызова инструментов

- Каждый вызов инструмента — это настоящий вызов с реальными аргументами,
  а не текстовый пример или плейсхолдер.
- Плейсхолдеры (`...`, `TODO`, `REPLACED_PLACEHOLDER` и т.п.) внутри
  аргументов реального вызова запрещены.
- После каждого вызова, изменяющего файл, результат немедленно проверяется
  повторным чтением файла в том же ответе, прежде чем сообщать об успехе.
- Если проверка показала, что изменение не применилось — попытка немедленно
  повторяется с точным содержимым, без переспрашивания пользователя.

### Правило: автономность исполнения

Остановка исполнения допустима только при наличии реального вопроса к
ассистенту от пользователя или необходимости уточнить у пользователя
неоднозначную трактовку задачи, риск непоправимого действия, либо
недостающие данные, которые невозможно получить самостоятельно.
Диагностика (чтение файлов, `git status`, `grep`) — часть выполнения
задачи, а не повод для промежуточной остановки с отчётом.

## Архитектурные принципы

### Проектная карта

- При изменении архитектуры, функционала или конфигурации обновлять
  проектную карту: `README.md`, `AGENTS.md`, `docs/`.
- Это правило гарантирует, что документация не отстаёт от кода.

### Чистая архитектура

Зависимости направлены внутрь:

```
Api → Application → Domain ← Infrastructure
```

**Domain** не зависит от внешних библиотек.

### CQRS vs CRUD (важно про терминологию)

- **Не называть CQRS** стандартный CRUD-шаблон (репозиторий/сервис с методами Create/Read/Update/Delete поверх одной модели и одной БД). Это просто разделение методов по действию, а не паттерн CQRS.
- Настоящий **CQRS** требует **логического разделения верхнеуровневых модулей** для команд (Commands) и запросов (Queries): отдельные модели, отдельные пути обработки (разные namespace/классы/handlers), а в идеале — **раздельные хранилища/инстансы БД** для чтения и записи (Read replica / отдельная read-модель), с явной синхронизацией между ними (например, через Domain Events).
- Если в модуле просто есть класс с методами `CreateAsync`, `GetAsync`, `UpdateAsync`, `DeleteAsync` над одной и той же таблицей/DbContext — это **CRUD**, и называть его CQRS в коде, документации, PR и коммитах **запрещено**.

### Целевой фреймворк

- Target framework: `net10.0` во всех проектах решения.

## Правила работы с базой данных (КРИТИЧНО)

### Database-First

- Схема БД ведётся единым каноническим SQL `tools/db/01_schema.sql`.
- На старте приложения авто-миграции/EnsureCreated запрещены.
- При несоответствии EF-модели и БД приоритет у канонических SQL;
  выравнивание через `HasColumnName(...)` и правку SQL, не EF-миграциями.

### SQL-файлы

| Файл | Назначение |
|------|------------|
| `00_reset_schema.sql` | DROP всех объектов + применение `01_schema.sql` |
| `01_schema.sql` | Каноническая схема БД (DDL: `CREATE TABLE`, индексы, ограничения) |
| `02_seed.sql` | Справочники и системные записи |
| `03_demo.sql` | Демонстрационные данные |

### Запрещено

- Прямые SQL-операции (`INSERT`, `UPDATE`, `DELETE`, `ALTER TABLE`, `TRUNCATE`, `DROP`) к БД.
- Миграции через `dotnet ef migrations` / `EnsureCreated` / `EnsureDeleted`.
- `ALTER TABLE ... ADD COLUMN` — в `01_schema.sql` только полные `CREATE TABLE`.
- `UPDATE` в seed-скриптах — значения задаются в `INSERT`.
- Предлагать пользователю «создать миграцию».

### Табличная нотация (snake_case)

- Имена таблиц и колонок — snake_case.
- PK: `id uuid`. FK: `<ref>_id`.
- Индексы: `ix_<table>_<col>`. Уникальные: `ux_<table>_<col>`.

### Обязательный маппинг EF-конфигурации (КРИТИЧНО)

При добавлении **любой** новой колонки в `01_schema.sql` **обязательно** добавлять
маппинг в EF-конфигурацию entity:
1. Добавить свойство в entity class (`src/Domain/Entities/`)
2. Добавить `.HasColumnName("column_name")` в конфигурацию
3. Без маппинга EF Core не генерирует колонку в SQL → ошибка времени выполнения

**Чек-лист при добавлении колонки:**
```
[ ] Колонка в 01_schema.sql
[ ] Свойство в entity class
[ ] Маппинг в EF-конфигурации (.HasColumnName)
[ ] DbSet в DbContext (если новая таблица)
```

### Запрет каскадных удалений (КРИТИЧНО)

`ON DELETE CASCADE` запрещён во всех FK-связях проекта.

Допустимые варианты `ON DELETE`:
- `ON DELETE RESTRICT` — для прямых потомков (нельзя удалить родителя, пока есть дети)
- `ON DELETE SET NULL` — для nullable FK (установить NULL при удалении)

### Атомарность обращений к БД (КРИТИЧНО)

**Все обращения к БД** (запросы на чтение и запись) **ОБЯЗАНЫ** выполняться в явной транзакции.

Исключения: операции, состоящие из единственного `SaveChangesAsync` без предшествующих `Add/Update/Remove` в контексте.

```csharp
await using var transaction = await ctx.Database.BeginTransactionAsync();
try
{
    // ... операции с БД
    await transaction.CommitAsync();
}
catch
{
    await transaction.RollbackAsync();
    throw;
}
```

## Правила конфигурации

### Конфигурация логирования (КРИТИЧНО)

- Все настройки логирования хранятся **исключительно в конфигурационном
  файле** (`appsettings.json` / переменные окружения), а не в базе данных
  и не в пользовательском интерфейсе.

### Запрет персональных данных в логах (КРИТИЧНО)

- В логи **запрещено** выводить: ФИО, ИНН, СНИЛС, данные ДУЛ (серия, номер).
- Разрешено логировать: `PersonId` (GUID), `SourceSystemId`, `ExternalPersonId`, статусы, коды ошибок.
- При ошибке — логировать только тип ошибки, идентификатор записи в сервисе (ИД), идентификатор системы источника и тип сущности (если есть), без содержания персональных данных.
- При логировании HTTP-запросов — не включать тело запроса, содержащее ПДн.

### Конфигурация внешних интеграций

- Все настройки внешних интеграций хранятся **исключительно в конфигурационном
  файле** (`appsettings.json` / переменные окружения).
- Хардкодинг URL, ключей или endpoints в коде запрещён.
- Рекомендуемый способ чтения: `IOptions<T>` (для интеграций с 3+ параметрами)
  или `IConfiguration["Section:Key"]` (для простых случаев).

### Чувствительные данные в конфигурации (КРИТИЧНО)

- **Ключи, пароли, токены и секреты** внешних интеграций **запрещено**
  хранить в `appsettings.json` и любых других файлах, отслеживаемых git.
- Чувствительные данные размещаются в `.env` (добавлен в `.gitignore`)
  или в переменных окружения.
- В `appsettings.json` чувствительные поля оставляются пустыми (`""`),
  интеграция — отключённой (`"Enabled": false`).

### Lazy Initialization для внешних интеграций (КРИТИЧНО)

- Конструкторы клиентов внешних интеграций **не выполняют сетевых соединений**.
  Подключение — при первом вызове метода (lazy), а не в конструкторе.
- Ошибки конфигурации **не должны крашить приложение**. Вместо
  `throw new InvalidOperationException` используется `Log.Warning` +
  fallback на значение по умолчанию или отключение интеграции.
- Опциональные интеграции регистрируются только при явном флаге `Enabled`.

## Правила кодирования

### Стиль C#

- Namespace: `Mnemonios.{Layer}.{Module}`
- Classes: PascalCase
- Interfaces: I + PascalCase
- Methods: PascalCase (с Async-суффиксом для асинхронных)
- Parameters: camelCase
- Private fields: _camelCase

### XML Documentation

Все публичные члены должны иметь XML-документацию:

```csharp
/// <summary>
/// Описание метода.
/// </summary>
/// <param name="param">Описание параметра.</param>
/// <param name="cancellationToken">Токен отмены.</param>
/// <returns>Описание возвращаемого значения.</returns>
public async Task<int> CreateAsync(
    CreateRequest request,
    CancellationToken cancellationToken = default)
```

### Dependency Injection

Внедрение зависимостей через конструктор:

```csharp
public class MyService : IMyService
{
    private readonly IRepository _repository;
    private readonly ILogger<MyService> _logger;

    public MyService(
        IRepository repository,
        ILogger<MyService> logger)
    {
        _repository = repository ?? throw new ArgumentNullException(nameof(repository));
        _logger = logger ?? throw new ArgumentNullException(nameof(logger));
    }
}
```

### Магические числа (КРИТИЧНО)

Числовые и строковые литералы, имеющие бизнес-смысл, **запрещено** оставлять инлайн.
Каждый такой литерал выносится в именованную константу:

```csharp
// ✅ Правильно
/// <summary>Отступ в пикселях при прокрутке.</summary>
private const int ScrollOffsetPx = 200;

var scrollLeft = (int)(...) - ScrollOffsetPx;
```

- Исключение: `0`, `1`, `-1` и другие «натуральные» числа базовой арифметики.
- Исключение: строки формата (`"dd.MM.yyyy"`), CSS-цвета.

### Паттерн Builder для сложных объектов (КРИТИЧНО)

При создании объектов с **≥ 4 параметрами** обязателен паттерн **Builder**
с валидацией в `Build()`.

### Обработка ошибок (КРИТИЧНО)

- Пустые блоки `catch { }` или `catch { /* ignore */ }` **запрещены**.
- Каждый `catch` должен как минимум логировать исключение.
- При логировании/показе ошибок БД — извлекать самое глубокое сообщение из
  цепочки `InnerException` (EF Core оборачивает реальную ошибку).

### Серверная валидация (КРИТИЧНО)

- **Все** операции записи обязаны иметь серверную валидацию.
- Клиентская валидация — удобство; серверная — защита данных.
- Сервер обязан проверять: обязательные поля, существование FK-ссылок,
  бизнес-правила, права доступа.

### Валидация FK-ссылок при записи (КРИТИЧНО)

При сохранении данных, содержащих внешние ключи (FK), **обязательно** проверять
существование связанной записи.

### try/catch оборачивает всё тело эндпоинта (КРИТИЧНО)

try/catch оборачивает **всё тело** — от создания DbContext до возврата результата.

### Логирование URL при ошибках HTTP-запросов (КРИТИЧНО)

При ошибке обращения к HTTP-сервису в лог **обязательно** выводится
полный URL запроса, код ответа и тело ошибки.

### URL в UI-сообщениях об ошибках HTTP

Каждое сообщение об ошибке HTTP-запроса, показываемое пользователю, **обязано**
содержать полный URL endpoint'а.

### Минимизация Program.cs — логика в сервисах (КРИТИЧНО)

- `Program.cs` содержит **только** регистрацию DI, middleware, конфигурацию
  приложения и minimalist API-групп.
- Бизнес-логика, валидация, работа с БД — **выносятся** в отдельные сервисы.

### ILogger в Minimal API — только ILoggerFactory (КРИТИЧНО)

- В Minimal API endpoint'ах использовать `ILoggerFactory` + `CreateLogger("Category.Name")`.
- Запрещено: `ILogger` (без generic), `ILogger<StaticClass>`.

### Формат имён лог-файлов

- Файлы приложения: `app-{yyyyMMddHH}.log` (Hourly).
- Файлы аудита: `audit-{yyyyMMddHH}.log` (Hourly).

### Аудит-лог vs лог приложения (КРИТИЧНО)

- Успешные операции CRUD пишутся в лог приложения (`ILogger`), а не в аудит-лог.
- Аудит-лог (`ISecurityAuditService`) — только для контроля доступа.

## Git Flow

| Ветка | Назначение | Защита |
|-------|------------|--------|
| `main` | Продакшн | 2 reviewers + CI |
| `develop` | Интеграция | 1 reviewer + CI |
| `feature/*` | Фичи | PR → develop |
| `bugfix/*` | Исправления | PR → develop |
| `hotfix/*` | Экстренные | PR → main + develop |

### Правило: первый коммит

Первый коммит в репозитории всегда имеет название `Initial commit`, независимо от
содержимого. Никаких `feat: ...`, `chore: initial scaffold` и т.п. — только
`Initial commit`.

### Правило: коммиты только по запросу пользователя (КРИТИЧНО)

Запрещено выполнять `git commit` без **явного** запроса от пользователя
(«закоммить», «коммитни», «сделай коммит», «push» и т.п.).
Коммит всегда сопровождается `git push` в том же ответе.

- Если пользователь не просил коммить — файлы остаются в working tree.
- При push возникает конфликт — вопрос выносится пользователю.
- **Согласование изменений ≠ разрешение на коммит.** Одобрение пользователем
  кода или запуск перезапуска приложения не является запросом на коммит.
  Коммит выполняется только при явной команде: «коммить», «push», «закоммить».

### Commit Message

```
<type>(<scope>): <description>

feat(module): add new feature
fix(module): correct bug
docs(api): update documentation
```

### Объединение коммитов (squash) одним действием (КРИТИЧНО)

- При необходимости объединить коммиты сессии используется:
  ```bash
  git reset --soft <базовый_коммит>
  ```
- Если базовый коммит — корневой (`Initial commit`), **не создавать новый коммит
  поверх**, а использовать `git commit --amend`:
  ```bash
  git reset --soft InitialCommitHash  # перемещает HEAD на Initial commit
  git commit --amend -m "Initial commit"
  ```
- `reset --soft` + отдельный `commit` на корневом коммите создаёт **два**
  коммита с одинаковым названием. `--amend` этого избегает.
- После squash — `git push --force-with-lease` (не `--force`).

## Правила тестирования

### Стек

- **xUnit**: Тестовый фреймворк
- **Moq**: Мокинг
- **FluentAssertions 6.12.0**: Утверждения (фиксация на 6.x — 7.x коммерческая)

### Покрытие

| Тип | Минимальное покрытие |
|-----|---------------------|
| Unit тесты | 80% |
| Integration тесты | 60% |
| Общее | 70% |

### Именование тестов

```csharp
[Fact]
public async Task MethodName_Condition_ExpectedResult()
{
    // Arrange
    // Act
    // Assert
}
```

### DB-валидаторы: тестирование через Moq (КРИТИЧНО)

- DB-валидаторы принимают абстракцию `IApplicationDbContext` (порт из Domain).
- В unit-тестах используется **Moq** для мока `IApplicationDbContext`.
- Запрещено передавать конкретные коллекции.

## Безопасность

### Проверка компонентов на уязвимости (CVE)

- При добавлении нового пакета/компонента проверять его на известные
  уязвимости (CVE) через GitHub Security Advisories, Snyk, NVD.

### Чувственные данные

- Не коммитьте секреты в репозиторий.
- Используйте `.env` для локальных настроек.
- Шифруйте PII данные на уровне приложения.

## Правила документации

- Каждая поддиректория `docs/` **обязана** содержать файл `README.md`.
- Статьи документации **не должны** содержать ссылок «Назад» в конце файла.
- Статьи группируются по тематическим подгруппам, а не хранятся в линейном списке.

## Правило: валидация X-Forwarded-For (КРИТИЧНО)

Заголовок `X-Forwarded-For` может быть пустым, отсутствовать или содержать
некорректные данные. При извлечении IP клиента **обязательна** валидация
через `IPAddress.TryParse`. Невалидный IP → fallback на `RemoteIpAddress`.
