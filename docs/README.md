# ЕДИН — Сервис единой идентификации физических лиц

Master Person Index (MPI) — обеспечивает определение единого физического лица по данным из различных информационных систем и выдачу стабильного `PersonID`.

---

## Назначение

**ЕДИН — единый сервис идентификации физических лиц для корпоративных информационных систем.**

**ЕДИН является частным случаем реестрового хаба**, поскольку хранит:
- **Системы-источники** (`sourceSystemId`) — информационные системы, передающие данные
- **Типы объектов** (`externalPersonType`) — классификацию записей во внешних системах (пациент, сотрудник, клиент и т.д.)
- **Идентификаторы записей** (`externalPersonId`) — внешние ключи, являющиеся источниками данных для золотой записи

При поступлении записи из внешней информационной системы сервис:
1. Нормализует и валидирует данные
2. Вычисляет идентификационные ключи (HMAC-SHA256)
3. Ищет совпадения в MPI
4. Возвращает существующий `PersonID` или создаёт новый
5. Сохраняет связь с внешней информационной системой
6. Фиксирует дефекты данных в таблице `person_defects`

### Терминология

| Термин | Определение |
|--------|-------------|
| **Master Identifier** | Мастер-идентификатор человека — внутренний `PersonID` (UUID), выдаваемый сервисом ЕДИН. Стабильный на протяжении всего жизненного цикла записи и неизменный при обогащении данными из других ИС. |
| **Evidence** | Доказательства идентичности — документы и данные, подтверждающие уникальность физического лица: ДУЛ (паспорт, ВУ и др.), СНИЛС, ИНН. ФИО **не являются** доказательствами идентичности и хранятся как есть, без нормализации идентификационного значения. |
| **Record References** | Ссылки на записи этого человека в других информационных системах. Передаются в поле `identifiers` запроса. Каждая ссылка состоит из: `sourceSystemId` (идентификатор системы-источника), `externalPersonId` (внешний ключ записи в этой системе), `externalPersonType` (тип записи, например «Пациент», «Сотрудник», «Клиент»). |

### Границы использования

| Категория | Сервис предназначен для | Сервис НЕ предназначен для |
|-----------|------------------------|---------------------------|
| Идентификация | Единое определение физического лица внутри корпоративного контура | Аутентификация или авторизация пользователей |
| Данные | Хранение ключей идентификации (HMAC-хеши) и связей с внешними системами | Полный комплект персональных данных (ФИО, ИНН, СНИЛС хранятся в усечённом/нормализованном виде) |
| Интеграция | Стабильный внутренний ИД (`PersonID`) для кросс-системной интеграции | Замена карточек учёта в учётных системах-источниках |
| Контроль | Валидация ИНН, СНИЛС, ДУЛ и контроль качества входных данных | Управление доступом к ресурсам |
| Передача | Передача хешей ключей и идентификаторов для сопоставления | Передача персональных данных третьим лицам |
| Согласие | Технический механизм удаления данных по запросу (cessation) | Хранение согласия на обработку ПДн и отзыв согласия — ответственность внешних систем |

> **Важно.** Хранение согласия на обработку ПДн и отзыв согласия на обработку ПДн **не являются** функциональными особенностями проекта ЕДИН. Эти функции возлагаются на одну или несколько вызывающих корпоративных информационных систем. ЕДИН предоставляет технический механизм удаления данных (`POST /persons/cessation`, `POST /persons/cessation/deferred`), но решение о необходимости отзыва принимает внешняя система-источник.

> **Ограничение передачи данных.** Вычисленные HMAC-хеши **не передаются** через API ни в ту, ни в другую сторону. Персональные данные (ФИО, ИНН, СНИЛС, ДУЛ) **не передаются** вызывающим системам через API — они хранятся в нормализованном виде исключительно для целей внутренней идентификации.

## Данные физического лица

| Поле | Обязательно | Описание |
|------|-------------|----------|
| `lastName` | Да | Фамилия |
| `firstName` | Да | Имя |
| `middleName` | Нет | Отчество |
| `evidence` | Нет | Объект доказательств идентичности (ИНН, СНИЛС, ДУЛ) |
| `evidence.inn` | Нет | ИНН (10 или 12 цифр, с проверкой контрольной суммы) |
| `evidence.snils` | Нет | СНИЛС (11 цифр, с проверкой контрольной суммы) |
| `evidence.dulType` | Нет | Тип документа (ПАСПОРТ, УДОСТОВЕРЕНИЕ и т.д.) |
| `evidence.dulSeries` | Нет | Серия документа (обязательно если указан `dulNumber`) |
| `evidence.dulNumber` | Нет | Номер документа (обязательно если указан `dulSeries`) |
| `identifiers` | Да | Массив ссылок на записи во внешних системах (Record References) |
| `identifiers[].sourceSystemId` | Да | Идентификатор внешней информационной системы |
| `identifiers[].externalPersonId` | Да | Идентификатор лица во внешней информационной системе |
| `identifiers[].externalPersonType` | Нет | Произвольный тип внешнего объекта |

## Толерантная обработка ошибок

Сервис **не отказывается** от добавления сведений о ФЛ при наличии ошибок в ИНН, СНИЛС или ДУЛ.

### Правила

| Поле | Поведение |
|------|-----------|
| `lastName`, `firstName` | **Обязательны** — без имени нельзя создать запись |
| `identifiers` | **Обязательны** — хотя бы один элемент массива обязателен (без привязки к информационной системе нет смысла в MPI) |
| ИНН с ошибкой контрольной суммы | **Пропускается** — ИНН не сохраняется, ключ не создаётся, дефект логируется |
| СНИЛС с ошибкой контрольной суммы | **Пропускается** — аналогично ИНН |
| ДУЛ без серии/номера | **Пропускается** — ДУЛ не сохраняется, дефект логируется |

### Типы дефектов

## Идентификационные ключи

Формируются HMAC-SHA256 хеши от нормализованных данных с секретным ключом из конфигурации.

Подробное описание ключей и алгоритма: [docs/hashes.md](hashes.md)

---

## Алгоритм идентификации

```
1. Валидация входных данных
2. Нормализация полей
3. Вычисление доступных ключей
4. Поиск person_id по ключам в БД
5. Решение:
   - 1 person_id → Matched (однозначное совпадение)
   - 0 person_id → Unmatched (создание нового лица)
   - >1 person_id → Conflict (противоречивые данные)
6. Привязка external_id к найденному/созданному лицу
```

Наличие неполных данных не препятствует сопоставлению — используются только доступные ключи.

## API

### POST /persons/resolve

Поиск или создание `PersonID`.

**Request:**
```json
{
  "lastName": "Иванов",
  "firstName": "Иван",
  "middleName": "Иванович",
  "evidence": {
    "inn": "7707083893",
    "snils": "12345678964",
    "dulType": "21",
    "dulSeries": "4510",
    "dulNumber": "123456"
  },
  "identifiers": [
    {
      "sourceSystemId": "CRM",
      "externalPersonId": "ext-12345",
      "externalPersonType": "client"
    }
  ]
}
```

**Поля запроса:**
- `lastName`, `firstName` — обязательны
- `middleName` — необязательно
- `evidence` — необязательный объект с доказательствами идентичности (ИНН, СНИЛС, ДУЛ)
- `identifiers` — обязательный массив ссылок на записи во внешних системах (Record References)
- `requestedPersonId` — необязательный UUID. Если передан:
  - Персона найдена → Matched (обогащение записи)
  - Персона не найдена → Unmatched (создание с указанным ID)

**Response (200 OK):**
```json
{
  "status": "Matched",
  "personId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

> Если установлен отложенный отзыв, в ответ добавляется поле `scheduledDeletionDate`:
> ```json
> {
>   "status": "Matched",
>   "personId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
>   "scheduledDeletionDate": "2026-12-31T23:59:59Z"
> }
> ```

**Статусы:**
- `Matched` — найдено однозначное соответствие
- `Unmatched` — нового лицо создано
- `Conflict` — обнаружены противоречивые данные (разные лица)

**Поля ответа:**
- `personId` — внутренний идентификатор ЕДИН (Golden ID)
- `scheduledDeletionDate` — дата запланированного удаления (только если установлен отложенный отзыв, иначе не возвращается)

### POST /persons/cessation

Прекращение обработки персональных данных. Универсальный endpoint для всех внешних систем.

Двухфазный подход:
1. **Фаза 1 (cessation):** пометить внешние ключи в `ext_person_cessations` (`processing_status = 'cessation'`). Золотые записи **НЕ** удаляются.
2. **Фаза 2 (reconcile):** `POST /persons/cessation/reconcile` — удалить помеченные staging-записи, затем если у лица нет оставшихся внешних ссылок — удалить золотые записи.

Подробное описание: [docs/reconciliation.md](reconciliation.md)

**Request:**
```json
{
  "identifiers": [
    {
      "sourceSystemId": "CRM",
      "externalPersonId": "ext-12345"
    }
  ]
}
```

**Response (200 OK):**
```json
{
  "personId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "deletedKeys": 5,
  "deletedExternalIds": 3,
  "deletedDefects": 1
}
```

**Response (404 Not Found):**
```json
{
  "error": "Физическое лицо не найдено по связи CRM/ext-99999."
}
```

**Response (400 Bad Request):**
```json
{
  "error": "Обязательное поле «Идентификатор внешней системы»."
}
```

### POST /persons/cessation/deferred

Отложенное прекращение обработки персональных данных. Данные будут удалены на указанную дату в будущем.

Если до наступления даты удаления те же ПДн будут добавлены снова (через `POST /persons/resolve`), отложенное прекращение автоматически отменяется.

**Request:**
```json
{
  "identifiers": [
    {
      "sourceSystemId": "CRM",
      "externalPersonId": "ext-12345"
    }
  ],
  "scheduledDeletionDate": "2026-12-31T23:59:59Z"
}
```

**Response (200 OK):**
```json
{
  "personId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "scheduledDeletionDate": "2026-12-31T23:59:59Z"
}
```

**Response (400 Bad Request):**
```json
{
  "error": "Дата удаления должна быть в будущем."
}
```

**Response (404 Not Found):**
```json
{
  "error": "Физическое лицо не найдено по связи CRM/ext-99999."
}
```

**Response (409 Conflict):**
```json
{
  "error": "Отложенное прекращение обработки уже запланировано для связи CRM/ext-12345 (дата удаления: 2026-12-31T23:59:59Z)."
}
```

### GET /persons/{personId}

Получение данных физического лица (без ПДн — только идентификаторы и метаданные).

**Response (200 OK):**
```json
{
  "personId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "createdAt": "2024-01-15T10:30:00Z",
  "identifiers": [
    {
      "sourceSystemId": "CRM",
      "externalPersonId": "ext-12345",
      "externalPersonType": "client"
    }
  ],
  "defects": [
    {
      "defectType": "invalid_inn",
      "defectMessage": "Некорректный ИНН: неверная контрольная сумма.",
      "fieldName": "inn"
    }
  ],
  "identificationKeys": [
    {
      "id": "b1c2d3e4-f5a6-7890-abcd-ef1234567890",
      "keyType": "fio",
      "normalizationVersion": 1,
      "createdAt": "2024-01-15T10:30:00Z"
    }
  ],
  "deferredCessations": [
    {
      "id": "c2d3e4f5-a6b7-8901-abcd-ef1234567890",
      "sourceSystemId": "CRM",
      "externalPersonId": "ext-12345",
      "scheduledDeletionDate": "2026-12-31T23:59:59Z",
      "status": "pending",
      "organizationUnitKey": "unit-001",
      "createdAt": "2024-06-01T12:00:00Z"
    }
  ]
}
```

> Примечание: персональные данные (ФИО, ИНН, СНИЛС, ДУЛ) не возвращаются вызывающим системам. Сервис хранит их в нормализованном виде исключительно для целей идентификации.
