ADR-001, ADR-002, ADR-005, ADR-009, ADR-022, ADR-023, ADR-030..036

## ADR-001: Выбор монолитной архитектуры

**Статус**: Принято

**Контекст**: Требование изолированного решения без внешних интеграций на первом этапе.

**Решение**: Модульный монолит с выделенными сервисами. Каждый доменный модуль — отдельный namespace с интерфейсами в Domain и реализациями в Infrastructure.

**Последствия**:
- Позитив: Простота развёртывания, транзакционность, контроль версий
- Негатив: Ограничения масштабирования (решается при необходимости)

## ADR-002: CQRS vs CRUD — терминологическое разграничение

**Статус**: Принято

**Контекст**: В коде и документации термин "CQRS" ошибочно применялся к обычным CRUD-репозиториям/сервисам, что размывало паттерн.

**Решение**: Зафиксировано строгое разграничение:
- **CRUD** — класс/сервис с методами `CreateAsync`, `GetAsync`, `UpdateAsync`, `DeleteAsync` над одной моделью и одним хранилищем. Используется по умолчанию.
- **CQRS** — применяется только там, где есть логическое разделение Command и Query (разные namespace/классы/handlers), с отдельными моделями для чтения и записи.
- Называть CRUD-реализацию "CQRS" в коде, PR, документации и коммитах запрещено.

**Последствия**:
- Позитив: Точность технической коммуникации, корректные ожидания от структуры модуля
- Негатив: Требуется ревизия существующих модулей при некорректном использовании термина

## ADR-005: Хранение настроек логирования исключительно в конфигурационном файле

**Статус**: Принято

**Контекст**: Риск смешения инфраструктурной конфигурации (уровни логирования, пути к файлам, форматы, ротация) с прикладными данными.

**Решение**: Все настройки логирования хранятся исключительно в конфигурационном файле (`appsettings.json` / переменные окружения) и считываются через стандартный механизм конфигурации ASP.NET Core (`IOptions<T>` / `IConfiguration`). Хранение этих настроек в базе данных или редактирование через UI запрещено.

**Последствия**:
- Позитив: единый источник истины, версионирование через git, совместимость с DevOps
- Негатив: изменение параметров требует передеплоя/перезапуска

## ADR-009: Серверная валидация — изолированный валидатор для каждой формы сохранения

**Статус**: Принято

**Контекст**: Каждая форма сохранения данных требует проверки корректности на стороне сервера. Клиентская валидация не гарантирует согласованности.

**Решение**:
1. Для каждой формы сохранения создаётся изолированный серверный валидатор — статический класс/метод в `Domain.Validation`, не зависящий от БД, DI-контейнера или HTTP-контекста.
2. Валидатор принимает plain-data модель (record) и возвращает результат со списком ошибок.
3. `Save()` вызывает валидатор первым действием, до любых операций с БД.

**Альтернативы**:
- Data Annotations — привязаны к EF-сущностям, не работают без DbContext.
- FluentValidation — добавляет внешнюю зависимость без необходимости.
- Только клиентская проверка — не защищает от прямых вызовов API.

**Последствия**:
- Позитив: полная изоляция от окружения, тестируется без моков
- Негатив: дублирование с клиентской валидацией (для UX); нужна синхронизация

## ADR-022: Все настройки внешних интеграций — в конфигурационном файле, не в коде

**Статус**: Принято

**Контекст**: В проекте добавляются внешние интеграции. Формального архитектурного решения, закрепляющего хранение настроек в конфиге, не было.

**Решение**: Все настройки внешних интеграций (URL API, ключи доступа, таймауты, флаги включения/отключения) хранятся **исключительно** в конфигурационном файле (`appsettings.json` / переменные окружения). Запрещено:
- Хардкодить URL, ключи или endpoints в коде
- Хранить настройки интеграций в базе данных
- Редактировать настройки интеграций через UI

Допустимые исключения:
- Значения по умолчанию (`Enabled: false` для опциональных интеграций)
- Endpoint'ы API, являющиеся частью контракта

**Последствия**:
- Позитив: единый источник истины, версионирование через git, совместимость с DevOps
- Негатив: изменение настроек требует передеплоя

## ADR-023: Lazy Initialization для внешних интеграций — приложение не падает при ошибках конфигурации

**Статус**: Принято

**Контекст**: Ошибка в конфигурации одной опциональной интеграции не должна приводить к аварийному завершению всего приложения.

**Решение**:

1. **Конструкторы клиентов не выполняют сетевых соединений** — подключение при первом вызове метода (lazy).
2. **Ошибки конфигурации не крашат приложение**:
   - `throw new InvalidOperationException` → `Log.Warning` + fallback
   - `int.Parse(...)` → `int.TryParse` с fallback-значением
   - Исключение: критичные для безопасности параметры (JWT-секрет) сохраняют `throw` в production
3. **Опциональные интеграции регистрируются только при явном флаге** `Enabled`.

**Последствия**:
- Позитив: приложение стартует даже при ошибках в конфигурации опциональных интеграций
- Негатив: ошибка конфигурации может остаться незамеченной до первого использования

## ADR-030: ЕДИН — batch-эндпоинт не реализуется

**Статус**: Принято

**Контекст**: Исходное ТЗ включало `POST /persons/resolve/batch` для массовых запросов.

**Решение**: Batch-эндпоинт не реализуется. `POST /persons/resolve` обрабатывает одну запись за вызов.

**Последствия**:
- Позитив: Простота реализации, каждая запись обрабатывается атомарно
- Негатив: Нет оптимизации для массовой загрузки

## ADR-031: ЕДИН — авторизация вызывающих систем отсутствует

**Статус**: Принято

**Контекст**: МПИ используется различными внешними информационными системами. Разграничение доступа не требуется на первом этапе.

**Решение**: Авторизация не реализуется. Все вызывающие системы имеют полный доступ.

**Последствия**:
- Позитив: Упрощение MVP
- Негатив: Нет разграничения доступа

## ADR-032: ЕДИН — HMAC ключ хранится в .env

**Статус**: Принято

**Контекст**: Секретный ключ HMAC-SHA256 используется для формирования идентификационных ключей.

**Решение**: Секретный ключ хранится в `.env` (в `.gitignore`) и читается через `IOptions<HmacSettings>`.

**Последствия**:
- Позитив: Простота настройки, секрет не попадает в git
- Нет ротации ключей

## ADR-033: ЕДИН — версионирование нормализации через поле в БД

**Статус**: Принято

**Контекст**: Правила нормализации могут изменяться. Старые ключи должны оставаться валидными.

**Решение**: Каждый ключ хранит `normalization_version` (INT, начальное значение = 1). При изменении алгоритма версия увеличивается в коде.

**Последствия**:
- Позитив: Сохранение истории ключей
- Незначительное увеличение объёма данных

## ADR-034: ЕДИН — системный пользователь откладывается

**Контекст**: BDR-013 требует таблицу `users` для аудит-полей. Модуль ЕДИН не содержит справочников `ref_*`.

- Аудит-поля `created_by` не используются

## ADR-035: ЕДИН — автоматическое слияние персон при совпадении ИНН

**Статус**: Принято

**Контекст**: При обработке данных из нескольких систем одно и то же лицо может быть создано как две разные записи (разные системы прислали одни и те же данные, но MPI не распознал их как одно лицо). При повторном resolve с ИНН, совпадающим ровно с одной из записей, есть возможность безопасно слить их.

**Решение**: В `PersonResolveService` при найденном >1 `person_id`:
1. Если в запросе есть ИНН и он совпадает ровно с 1 лицом → это лицо выживает, остальные сливаются через `PersonMergeService.MergePersonsAsync()`.
2. Если ИНН совпадает с несколькими или отсутствует → **Conflict**.

`PersonMergeService` переносит в выживающее лицо:
- Ключи идентификации
- Внешние идентификаторы
- Документы

После переноса сливаемое лицо удаляется.

**Последствия**:
- Позитив: автоматическое разрешение дублей, устранение рассогласованных записей
- Негатив: при невалидном ИНН возможен некорректный auto-merge (минимизируется валидацией ИНН)

Реализация:
- `PersonMergeService` — `src/Infrastructure/Services/PersonMergeService.cs`
- `PersonResolveService.ResolveByMatchingAsync` — вызов merge при >1 лица + ИНН

## ADR-036: ЕДИН — удаление standalone-ключей fio и fio_full

**Статус**: Принято

**Контекст**: ФИО не является сильным доказательством идентичности — множество людей имеют одинаковые ФИО. Standalone-ключи `fio` и `fio_full` создавали ложные срабатывания при идентификации.

**Решение**: Ключи `fio` и `fio_full` **не создаются** в `IdentificationKeyService.ComputeKeys()`. ФИО используется **только** в составе комбинированных ключей (`inn_fio`, `snils_fio`, `dul_fio`), где вклад ФИО усилен другими доказательствами.

**Последствия**:
- Позитив: снижение ложных срабатываний, чище результат matching
- Нет негативных: комбинированные ключи полностью покрывают сценарии идентификации

Реализация:
- `IdentificationKeyService.ComputeKeys` — удалены standalone `fio` и `fio_full`
- `AGENTS.md` → терминология Evidence: ФИО не являются доказательствами идентичности
